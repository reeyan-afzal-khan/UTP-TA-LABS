\section{What an operating system actually does}
An \term{operating system (OS)} is both a \emph{resource manager} and an \emph{abstraction layer}. Applications want convenient objects such as processes, files, sockets, and virtual addresses. Hardware provides processors, physical memory, disks, timers, and devices. The OS maps the convenient abstractions onto the physical resources while enforcing protection and sharing rules.

\section{Kernel mode and user mode}
Modern CPUs provide at least two privilege levels. Normal applications execute in \term{user mode}, where privileged instructions and direct hardware access are restricted. The kernel executes in \term{kernel mode}. A controlled transition occurs when a process performs a \term{system call}, when an interrupt arrives, or when an exception occurs.

\begin{intuition}
User mode is a safety boundary. A buggy application should be able to crash itself without being allowed to overwrite another process's memory or reprogram a disk controller directly.
\end{intuition}

\section{System calls are the operating-system API}
A system call requests a service that requires kernel authority. Typical families include:
\begin{itemize}
  \item \textbf{Process control:} create, terminate, wait, execute another program.
  \item \textbf{File management:} open, read, write, seek, close, inspect metadata.
  \item \textbf{Device management:} read/write devices and configure device-specific state.
  \item \textbf{Information:} process identifiers, time, resource limits, system information.
  \item \textbf{Communication:} pipes, shared memory, message queues, sockets, signals.
  \item \textbf{Protection:} permissions, identities, access checks, isolation.
\end{itemize}

\section{One program, several OS subsystems}
Suppose a shell launches a program that reads a file and prints a result. The shell creates a process; the scheduler chooses when it runs; virtual memory gives it an address space; the file system resolves the pathname; the storage stack reads disk blocks; device interrupts report I/O completion; the terminal receives the output.

\begin{keyidea}
The course topics are not separate features. They are cooperating subsystems required for almost every non-trivial program execution.
\end{keyidea}

\section{Process, program, and thread}
A \term{program} is passive code and data stored somewhere. A \term{process} is an executing instance with state: registers, program counter, address space, open files, scheduling information, and credentials. A \term{thread} is an execution stream inside a process; threads in the same process usually share the address space and open-file table while keeping separate registers and stacks.

\section{A process-state model}
A useful simplified model is \emph{new, ready, running, waiting, terminated}. A scheduler dispatches a ready process; an I/O request can move a running process to waiting; completion returns it to ready; preemption can move running back to ready.

\begin{chapterrecap}
\begin{itemize}
  \item The OS provides abstractions while managing and protecting hardware resources.
  \item System calls are controlled entry points from user programs into kernel services.
  \item Processes are resource-bearing execution instances; threads are execution flows within them.
  \item Scheduling, memory, I/O, and file systems cooperate during ordinary program execution.
\end{itemize}
\end{chapterrecap}
