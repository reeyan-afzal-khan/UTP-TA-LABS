\section{Concurrency creates interleavings}
Two threads can be individually correct yet jointly incorrect because their instructions can interleave in many possible orders. A \term{race condition} occurs when the result depends on an uncontrolled relative timing of concurrent operations on shared state.

\begin{workedexample}
Suppose shared \texttt{x=10} and two threads both execute \texttt{x=x+1}. At machine level this is conceptually read, add, write. Both threads can read 10 before either writes, then both write 11. The expected mathematical result 12 is lost. This is a \term{lost update} race.
\end{workedexample}

\section{The critical-section problem}
A \term{critical section} is code that accesses shared state requiring controlled concurrency. A classic solution aims for three properties:
\begin{description}
  \item[Mutual exclusion] At most one participant is in the protected critical section when simultaneous access would be unsafe.
  \item[Progress] If nobody is inside and some processes want to enter, the choice of the next entrant should not be postponed forever by unrelated processes.
  \item[Bounded waiting] A requester should not be bypassed indefinitely.
\end{description}

\section{Atomic operations and locks}
A lock works only if the operation that acquires ownership is itself atomic. Real processors provide primitives such as test-and-set or compare-and-swap, and OS/runtime libraries build mutexes and semaphores on top of such mechanisms plus scheduler support.

\subsection{Mutex}
A \term{mutex} expresses ownership of one mutually exclusive region. A thread locks it, enters the critical section, then unlocks it.

\subsection{Semaphore}
A \term{semaphore} is an integer-like synchronization abstraction manipulated through atomic operations often called wait/P/down and signal/V/up.
\begin{itemize}
  \item A \textbf{binary semaphore} can act similarly to a lock in simple cases.
  \item A \textbf{counting semaphore} represents multiple units of an available resource.
\end{itemize}

\section{Producer-consumer with bounded buffer}
For a buffer of capacity $N$, the canonical semaphore design uses:
\[
\texttt{empty}=N,\qquad \texttt{full}=0,\qquad \texttt{mutex}=1.
\]
A producer must reserve an empty slot and enter the critical section before inserting an item; a consumer must reserve a full slot and enter the critical section before removing one.

\begin{pitfall}
The Lab 5 producer-consumer program changes ordinary integer variables through homemade \texttt{wait()} and \texttt{signal()} functions. This illustrates semaphore \emph{logic}, but it is not a real concurrent synchronization implementation because those operations are not made atomic and the program does not create concurrent producer/consumer threads.
\end{pitfall}

\section{System V shared memory in the lab}
The Lab 5 shared-memory program demonstrates the lifecycle of a shared segment:
\begin{mlsteps}
  \item Obtain/create a segment identifier with \texttt{shmget()}.
  \item Attach it into the process address space with \texttt{shmat()}.
  \item Read or write the mapped bytes.
  \item Detach with \texttt{shmdt()}.
  \item Remove the segment with \texttt{shmctl(..., IPC\_RMID,...)} when no longer needed.
\end{mlsteps}
Attaching shared memory does not automatically synchronize readers and writers. If multiple processes modify it concurrently, a separate synchronization scheme is required.

\section{Safety, liveness, and performance}
Concurrency design should be evaluated on three axes:
\begin{itemize}
  \item \textbf{Safety:} nothing bad happens, e.g. no two writers corrupt a protected structure.
  \item \textbf{Liveness:} something good eventually happens, e.g. no permanent deadlock/starvation.
  \item \textbf{Performance:} synchronization does not serialize more work than necessary or cause excessive contention.
\end{itemize}
Correctness comes first; a very fast data race is still wrong.
