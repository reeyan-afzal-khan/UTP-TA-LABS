\labsection{8}{Deep learning II: an LSTM for time series}{sec:lab08-lstm}

\begin{labproject}{Forecast the next hour of bike demand from the previous twenty-four}
\textbf{Read first.} Chapter~\ref{ch:deep}, and the time-split rule in Chapter~\ref{ch:data}.\\
\textbf{Goal.} Turn a time series into supervised windows with a chronological split, set two naive baselines any forecast must beat, train an LSTM and read its curve, look at its forecasts hour by hour, and save the weights with the scaling they depend on.\\

\labpart{Part A --- From a series to windows}

\begin{labquestion}{2}{Read and scale the series}
The hourly bike file from Lab~2 is one long series: 17,379 hourly rental counts in date order. A sequence model does not take a table of features; it takes the last few values and predicts the next one. The series is first scaled by the largest value in the training period, so that the network sees numbers near $[0,1]$.
\end{labquestion}

\textbf{What it means.} The scale is a training-set statistic, so it is computed before anything sees the validation period. The validation period does go higher, to 977, so a few validation inputs slightly exceed 1. That is correct, and a sign that no future value leaked into the scale. One caveat about the series itself: the two years contain 17,544 hours, so 165 have no row, mostly in the small hours. A window of 24 is really 24 rows. It spans exactly 24 hours in 90\% of all windows and 97\% of validation windows, and this lab, like most first forecasts, lets that go.
\end{labanswer}

\begin{labquestion}{3}{Build the windows and split by date}
A \emph{window} turns the series into rows: the 24 values before hour $t$ are the input, and the value at hour $t$ is the label. Sliding the window one hour at a time gives one row per hour. Because neighboring rows overlap, the split has to be chronological: the first 80\% of windows train, and the rest validate.
\end{labquestion}

\labpart{Part B --- Two forecasts that cost nothing}

\begin{labquestion}{4}{Compute two free forecasts}
Before any network is trained, two naive forecasts set the bar. \emph{Persistence} predicts that the next hour equals the last hour. \emph{Same hour yesterday} predicts the value 24 rows earlier, which is the first value in each window. A model that cannot beat both has learned nothing worth its cost.
\end{labquestion}

\begin{labquestion}{11}{One solution}
Three lookback lengths, then a wider hidden state, each trained for the same eight epochs.
\end{labquestion}
\begin{labanswer}
\lstinputlisting[style=utppython,firstline=203,lastline=232]{all_experiments/lab08_deep_learning_lstm_worked.py}
\begin{refoutput}
\begin{lstlisting}[style=utpterminal]
lookback =  6 hours, hidden = 32: validation MAE = 54.7 rentals
lookback = 24 hours, hidden = 32: validation MAE = 41.9 rentals
lookback = 48 hours, hidden = 32: validation MAE = 43.4 rentals
lookback = 24 hours, hidden = 64: validation MAE = 36.4 rentals
\end{lstlisting}
\end{refoutput}

\textbf{What it means.} Six hours of history is clearly worse: the network cannot see yesterday's value for this hour, which is a very useful clue. Forty-eight hours is no better than twenty-four, because one day already contains the daily shape. Doubling the hidden state does help, 36 against 42 rentals, and it roughly quadruples the weights.
\end{labanswer}

\begin{expectedfindings}
\begin{enumerate}
  \item It goes on falling, unevenly: 38.0 at epoch 12, 35.1 at epoch 14, 37.7 at epoch 16. Epoch-to-epoch wobble of about 2 rentals is noise, so a real run would keep the best epoch on validation.
  \item MAE 35.1 after 8 epochs, better than the 36.4 from doubling the hidden size, and at almost no cost in weights. The network no longer has to infer the time of day from the shape of the last 24 hours. A good feature can beat more capacity, as in Lab~1.
  \item The 8 a.m.\ hour is the hardest, with an MAE of about 109, followed by 10 a.m.\ (77) and the evening rush at 5 and 6 p.m.\ (69 and 66). Between 1 and 6 a.m.\ it is about 20. On hours above 500 rentals the MAE is about 81, and the forecast runs about 41 below the truth on average, so the network under-forecasts its peaks, as an averaging loss tends to.
\end{enumerate}
\end{expectedfindings}

\begin{troubleshoot}
\begin{description}
  \item[Validation MAE in the hundreds] You are measuring in scaled units or forgot to multiply back by \texttt{scale}. Baselines and model must use the same units.
  \item[A baseline looks suspiciously good] Check the alignment: \texttt{windows[cut:, -1]} is the hour before the target, and \texttt{windows[cut:, 0]} the same hour yesterday. An off-by-one error can compare a target with itself.
  \item[\texttt{Expected 3D input}] An LSTM with \texttt{batch\_first=True} needs (rows, steps, values per step). \texttt{unsqueeze(-1)} adds the last dimension.
  \item[Very slow on a CPU] Lower the number of epochs only for a quick test. The hidden size of 64 and the lookback of 48 are the slow runs.
\end{description}
\end{troubleshoot}
