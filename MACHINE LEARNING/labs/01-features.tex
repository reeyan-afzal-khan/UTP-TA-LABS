\labpartopen{Part B}{Feature engineering}{Questions 5--7 \textbullet\ Data: hotel bookings}{Turn nights, guests, lead time and booking history into five new columns, and measure whether they help a model.}

\begin{labquestion}{5}{Engineer five new columns}
Feature engineering means building inputs the model cannot see on its own. \texttt{total\_nights} adds the weekend and week nights, \texttt{total\_guests} adds the adults, children and babies, and \texttt{with\_children} flags a family; the four blank \texttt{children} counts are read as none. \texttt{log\_lead\_time} takes $\ln(1+x)$ of the days booked ahead, because a few bookings were made up to two years early and would otherwise stretch the scale. \texttt{cancelled\_before} flags a customer who has cancelled a booking before. Every new column uses only what was known when the booking was made, which is the test each feature must pass.
\end{labquestion}

\textbf{What it means.} Your warm-up should match the first column: 6 nights, 3 guests, a family, and $\ln 133 = 4.89$. The city booking was made 6 days ahead, so its \texttt{log\_lead\_time} is $\ln 7 = 1.95$. The logarithm squeezes long lead times together: 132 days is 22 times 6 days, but 4.89 is only 2.5 times 1.95, so the few bookings made a year or two ahead no longer dominate a linear model. Each column reads only its own booking's fields, so it is a fixed rule that may run before the split. Do not use \texttt{is\_canceled} to construct an input.
\end{labanswer}

\begin{labquestion}{11}{Compare feature sets, and see leakage}
Four feature sets are compared with the same logistic regression. \texttt{SelectKBest} keeps the ten encoded columns whose averages differ most between yes and no, and the L1 penalty shrinks weak coefficients all the way to zero and so selects on its own. Both selectors sit \emph{inside} the pipeline, after encoding, so they only ever see training rows. The fourth run adds \texttt{duration} back on purpose, to show what leakage looks like. Average precision is printed beside ROC AUC; with 11\% positives, it is the stricter of the two.
\end{labquestion}
\begin{labanswer}
\lstinputlisting[style=utppython,firstline=227,lastline=267]{all_experiments/lab01_features/lab01_features_worked.py}
\begin{refoutput}
\begin{lstlisting}[style=utpterminal]
all 19 features              ROC AUC = 0.802   average precision = 0.452
SelectKBest, k=10            ROC AUC = 0.791   average precision = 0.435
L1 penalty (selects itself)  ROC AUC = 0.801   average precision = 0.449
all 19 + duration (leakage)  ROC AUC = 0.939   average precision = 0.595

\textbf{What it means.} Ten columns do almost as well as all of them, and the L1 penalty matches the full model, so much of the table is noise for this task, and a selector inside the pipeline costs little. Guessing at random scores ROC AUC 0.5 and average precision 0.113, the share of yes answers, which is the true scale of these gains. The leaked column lifts ROC AUC to 0.939. That looks like a triumph and is a broken experiment, because nobody knows how long a call will last before making it. The dataset's own documentation says the same, and keeps \texttt{duration} only for benchmarks.
\end{labanswer}
