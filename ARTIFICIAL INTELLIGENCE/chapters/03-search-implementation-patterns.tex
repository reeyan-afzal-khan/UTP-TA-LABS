\section{One result type for every algorithm}

Every algorithm returns the same frozen dataclass, allowing one benchmark loop to compare them:

\begin{lstlisting}[style=aipython]
@dataclass(frozen=True)
class SearchResult:
    found: bool
    path: list
    hops: int
    path_cost_km: float
    expanded: int
    max_frontier: int
    runtime_ms: float

    def as_dict(self) -> dict:
        return asdict(self)
\end{lstlisting}

Three design decisions are hidden in those seven fields.

\begin{description}
  \item[The cost is recomputed from the path.] A helper sums edge weights after search, rather than using its stored $g$, keeping \texttt{path\_cost\_km} consistent with the returned path.
  \item[Failure has a shape.] An unreachable goal returns \texttt{found=False}, an empty path, \texttt{hops=-1} and infinite cost. Callers check \texttt{result.found}.
  \item[Effort is part of the answer.] \texttt{expanded} and \texttt{max\_frontier} are counted inside the loop, so every comparison in Labs 1--3 comes from the same counters.
\end{description}

\texttt{as\_dict()} converts a result into a pandas row via \texttt{\{**result.as\_dict()\}}, as used in every lab metrics file.

\section{Priority queues and tuple ordering}

Python's \texttt{heapq} pops the smallest tuple, comparing element by element from the left. The frontier entries in \texttt{best\_first} are \texttt{(priority, counter, state, g)}, and the \texttt{counter} is there for a reason (\figref{fig:tuple}).

\begin{aifig}[How heapq breaks priority ties]{Heap tuples compare left to right. A unique counter breaks priority ties by insertion order, avoiding comparisons between states.}{fig:tuple}

  {Without the counter the heap would compare the states. Strings compare, so airports
   happen to work --- but a tuple state or a mixed type raises \texttt{TypeError}, and even
   when it works the tie is broken by name rather than by the search.};
\end{tikzpicture}
\end{aifig}

\begin{pitfall}
Placing a payload directly after the priority makes ties depend on payload comparisons and possibly state names. Insert a unique increasing counter to resolve ties by insertion order without comparing payloads.
\end{pitfall}

\section{Testing search code}

A successful run on 6,464 airports can hide wrong costs, expansion counts or cycle handling. Tiny graphs make these errors hand-checkable. \texttt{utils/test\_search.py} contains eight tests, one per failure mode:

\begin{mltable}
\begin{tabularx}{\linewidth}{@{}>{\bfseries\leavevmode\color{MLNavy}}p{0.34\linewidth}X@{}}
\toprule
\rowcolor{MLPaleBlue!92}
Test & What a failure would mean \\
\midrule
start equals goal & The goal test runs before any expansion; hops and cost are zero. \\
unreachable goal & Failure is reported as \texttt{found=False}, not an exception or a wrong path. \\
cycles terminate & The seen-set stops DFS from looping forever. \\
BFS and UCS optimise different objectives & The two algorithms give different answers on a graph built so that they must. \\
frontier update finds the cheaper path & A state first reached expensively is later replaced by a cheaper route. \\
A$^\star$ matches UCS with a consistent heuristic & The optimality guarantee holds on a hand-checked graph. \\
GBFS is not assumed optimal & The test asserts the \emph{expected} suboptimality rather than pretending it away. \\
negative cost is rejected & The precondition of UCS is enforced with a clear error. \\
\bottomrule
\end{tabularx}
\end{mltable}

One test in full shows the pattern --- a tiny graph, a hand-derived expectation, one assertion:

\begin{lstlisting}[style=aipython]
def test_frontier_update_finds_cheaper_path():
    graph = {"A": [("B", 10.0), ("C", 1.0)], "C": [("B", 1.0)], "B": [("G", 1.0)], "G": []}
    result = ucs(graph, "A", "G")
    assert result.path == ["A", "C", "B", "G"]
    assert result.path_cost_km == pytest.approx(3.0)
\end{lstlisting}

These dataset-free tests import only \texttt{core}, run in under a second, and can run on any machine or continuous-integration server.

\begin{keyidea}
Test the algorithm on the smallest graph that can expose the bug, and test the dataset loader separately. A test that needs real data to run tests both at once and diagnoses neither.
\end{keyidea}

\section{A command-line interface}

\texttt{utils/\_\_main\_\_.py} makes the package runnable outside a notebook:

\begin{lstlisting}[style=aiterminal]
cd all_experiments
python -m utils --algorithm astar --start KUL --goal KEF
ASTAR: found=True, hops=4, cost_km=11461.3, expanded=69, runtime_ms=4.20
KUL -> HKT -> LED -> HEL -> KEF
\end{lstlisting}

The thirty-line module parses three options, loads the graph, selects an algorithm and prints its result. It calls existing search and cleaning code, reproducing Lab~2\textquotesingle s answer. Lab~3 runs it as a subprocess and checks exit status~0.

\section{Benchmarking fairly}

Lab~3 benchmarks BFS, UCS, GBFS and A$^\star$ on ten route pairs in \texttt{utils/search\_queries.csv}:

\begin{mltable}
\begin{tabularx}{\linewidth}{@{}>{\bfseries\leavevmode\color{MLNavy}}p{0.12\linewidth}>{\centering\arraybackslash}X>{\centering\arraybackslash}X>{\centering\arraybackslash}X>{\centering\arraybackslash}X@{}}

\midrule

UCS & 1.0 & 14,321 & 2.2 & 2,700 \\
GBFS & 1.0 & 15,087 & 2.1 & 2.1 \\
A$^\star$ & 1.0 & 14,321 & 2.2 & 63 \\
\bottomrule
\end{tabularx}

The notebook enforces four conditions for a fair comparison:

\begin{itemize}
  \item \textbf{Same graph, same queries, same machine.} Every algorithm sees the identical cleaned graph and the identical ten pairs.
  \item \textbf{Success rate before averages.} Averaging only solved queries hides failures on hard cases. All four methods solve all ten queries here.
  \item \textbf{Effort in expansions, not milliseconds.} The runtime column is kept but is not the basis for conclusions.
  \item \textbf{Every path validated.} The notebook checks that A$^\star$'s cost equals UCS's on all ten queries and counts the queries on which GBFS is costlier (seven of ten).
\end{itemize}

For these kilometre-based queries, A$^\star$ matches UCS at 2\,\% of its effort. Choose BFS for fewest legs and GBFS when reduced effort matters more than optimal cost.
