\section{The generic graph-search loop}

The methods share the following control flow.

\begin{lstlisting}[style=mlpython]
frontier = make_frontier(start)
visited = set()

while frontier:
    state, path, cost = remove_next(frontier)

    if state == goal:
        return path, cost

    if state in visited:
        continue
    visited.add(state)

    for successor in successors(state):
        add_to_frontier(frontier, successor, path, cost)
\end{lstlisting}

What changes is \texttt{remove\_next} and the priority attached to each state.

\subsection{Graphs}
A graph dictionary directly maps a node to its neighbors. Weighted graphs map to \((\text{neighbor},\text{cost})\) pairs.

\begin{lstlisting}[style=mlpython]
graph = {
    'A': [('B', 1), ('C', 4)],
    'B': [('D', 3), ('E', 2)],
    'C': [('F', 5)],
    'D': [('G', 4)],
    'E': [('G', 1)],
    'F': [('G', 2)],
    'G': []
}
\end{lstlisting}

\subsection{Grids}
A grid does not list neighbors explicitly. The successor function computes adjacent coordinates and checks bounds and cell conditions.

\begin{lstlisting}[style=mlpython]
for dx, dy in [(-1, 0), (1, 0), (0, -1), (0, 1)]:
    nx, ny = x + dx, y + dy
    if 0 <= nx < rows and 0 <= ny < cols:
        # apply the problem's wall or cost rule here
        ...
\end{lstlisting}

\subsection{Word ladders}
The Lab 3 GBFS example stores valid one-letter transitions explicitly as a graph. The heuristic compares the current word with the goal.

\begin{lstlisting}[style=mlpython]
def greedy_word_ladder(words, start, goal):
    import heapq

    def h(w):
        return sum(1 for a, b in zip(w, goal) if a != b)

    pq = [(h(start), [start])]
    visited = set()

    while pq:
        _, path = heapq.heappop(pq)
        current = path[-1]
        if current == goal:
            return path

        if current in visited:
            continue
        visited.add(current)
        for neighbor in words.get(current, []):
            if neighbor not in visited:
                heapq.heappush(pq, (h(neighbor), path + [neighbor]))
    return None
\end{lstlisting}

\subsection{Trees}
Tree traversal uses child references instead of a graph dictionary. BFS enqueues children; DFS recursively visits them.

\begin{lstlisting}[style=mlpython]
def bfs_tree(root):
    from collections import deque
    if not root:
        return []

    queue = deque([root])
    result = []
    while queue:
        node = queue.popleft()
        result.append(node.val)
        if node.left:
            queue.append(node.left)
        if node.right:
            queue.append(node.right)
    return result
\end{lstlisting}

\section{Path storage as a teaching device}

The teaching implementations store the full path in each frontier entry:

\begin{lstlisting}[style=mlpython]
queue.append(((nx, ny), path + [(nx, ny)]))
\end{lstlisting}

\begin{intuition}
Path copying simplifies traces and permits immediate path return, although larger systems often store parent links to reduce memory use.
\end{intuition}

\section{Visited-state discipline}

The examples update visited sets at slightly different points. The purpose is always the same: avoid processing a state repeatedly.

\section{Priority queues and tuple ordering}

Python's \texttt{heapq} removes the smallest tuple lexicographically. The laboratory code intentionally places the numerical priority first:

\begin{lstlisting}[style=mlpython]
# UCS
heapq.heappush(pq, (cost + weight, path + [neighbor]))

# GBFS
heapq.heappush(pq, (heuristic((nx, ny), goal), path + [(nx, ny)]))

# A*
heapq.heappush(pq, (new_g + heuristic((nx, ny), goal),
                    new_g,
                    path + [(nx, ny)]))
\end{lstlisting}

The first tuple element sets priority; later fields carry cost or path data.
\figref{fig:tuple} shows what \texttt{heapq} actually compares.

\begin{pitfall}
When two priorities tie, Python moves on to the \emph{next} tuple element --- and in the code above that is the path list. Comparing two lists compares their elements, so this only works while every state is mutually comparable.

The lab states are homogeneous (all strings, or all coordinate tuples), so the ties resolve quietly and the code runs. Mix the types and the same line raises at run time:

\begin{lstlisting}[style=mlpython]
heapq.heappush(pq, (4, ['A', 1]))
heapq.heappush(pq, (4, ['A', 'B']))
# TypeError: '<' not supported between instances of 'str' and 'int'
\end{lstlisting}

It is also a correctness smell even when it works: the tie is broken by whichever path happens to sort first, so the algorithm's output depends on state names rather than on the search.

The fix is one unique increasing integer between the priority and the payload, which makes ties resolve by insertion order and stops the payload from ever being compared:

\begin{lstlisting}[style=mlpython]
counter = 0
...
counter += 1
heapq.heappush(pq, (cost + weight, counter, path + [neighbor]))
\end{lstlisting}
\end{pitfall}

\section{A single comparison harness}

Run all compatible algorithms through one reporting function:

\begin{lstlisting}[style=mlpython]
def show_result(name, result):
    print(f"\n{name}")
    if result is None:
        print("No path found")
    else:
        print(result)
\end{lstlisting}

Compare two questions:
\begin{enumerate}
  \item Did the algorithm find a goal?
  \item What rule caused it to choose this particular path or cost?
\end{enumerate}

\begin{quickcheck}
\begin{enumerate}
  \item Which one line changes conceptually when you move from UCS to GBFS: successor generation or priority calculation?
  \item Why can the same Manhattan heuristic function be reused in GBFS and A*?
  \item What is the purpose of carrying \texttt{g} separately from \texttt{f} in the A* heap entry?
  \item In a tree, what plays the role of the successor function used by graph search?
\end{enumerate}
\end{quickcheck}

\begin{checkanswers}
\begin{enumerate}
  \item The priority calculation changes; successor generation can remain identical.
  \item Both methods need the same estimate of remaining grid distance, although A* also includes \(g\).
  \item The algorithm needs \(g\) to extend the path correctly; \(f\) alone mixes known and estimated cost.
  \item Reading the current node's child references produces its successors.
\end{enumerate}
\end{checkanswers}

\begin{chapterrecap}
\begin{itemize}
  \item The five search algorithms in Labs 1--3 share one generic search loop.
  \item Graphs, grids, words, and trees differ mainly in how successors are generated.
  \item Queue, stack/recursion, and heap data structures encode the frontier policy.
  \item Visited sets protect graph search from loops and repeated expansions.
  \item The templates make path, cost, and priority explicit.
\end{itemize}
\end{chapterrecap}
