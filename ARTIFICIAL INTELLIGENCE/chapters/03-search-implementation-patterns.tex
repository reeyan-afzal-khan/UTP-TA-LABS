\section{The pluggable frontier}

Every search program in this course has four parts, and three of them are fixed by the problem. The state representation and the successor function come from the graph; the goal test comes from the query. Only the frontier policy is a design choice, and that single choice names the algorithm (\figref{fig:pluggable}).

\begin{aifig}[The pluggable frontier policy]{The four components of every search program in this course. Three are fixed by the problem; only the frontier policy is chosen by the programmer, and that one choice is what names the algorithm.}{fig:pluggable}

\texttt{utils/core.py} takes this literally. BFS and DFS are two short functions that differ in \texttt{popleft} versus \texttt{pop}. UCS, GBFS and A$^\star$ are one function, \texttt{best\_first}, with a \texttt{mode} argument that selects the priority; \texttt{ucs}, \texttt{gbfs} and \texttt{astar} are one-line wrappers around it. When Lab~2 needed weighted A$^\star$, no new search code was written --- the heuristic was multiplied by 1.5 and passed to the same function.

\section{One result type for every algorithm}

A benchmark loop can only compare algorithms that return the same thing. \texttt{utils} defines one frozen dataclass and every function returns it:

\begin{lstlisting}[style=aipython]
@dataclass(frozen=True)
class SearchResult:
    found: bool
    path: list
    hops: int
    path_cost_km: float
    expanded: int
    max_frontier: int
    runtime_ms: float

    def as_dict(self) -> dict:
        return asdict(self)
\end{lstlisting}

Three design decisions are hidden in those seven fields.

\begin{description}
  \item[The cost is recomputed from the path.] \texttt{path\_cost\_km} is the sum of the edge weights along the returned path, computed by a helper after the search finishes, not the $g$ value the search happened to carry. The reported cost and the reported path can therefore never disagree.
  \item[Failure has a shape.] An unreachable goal returns \texttt{found=False}, an empty path, \texttt{hops=-1} and an infinite cost, so a caller can test \texttt{result.found} instead of catching an exception or checking for \texttt{None}.
  \item[Effort is part of the answer.] \texttt{expanded} and \texttt{max\_frontier} are counted inside the loop, so every comparison in Labs 1--3 comes from the same counters.
\end{description}

\texttt{as\_dict()} is what turns a result into a row of a pandas table with one expression, \texttt{\{**result.as\_dict()\}}, which is how every metrics file in the labs is built.

\section{Priority queues and tuple ordering}

Python's \texttt{heapq} pops the smallest tuple, comparing element by element from the left. The frontier entries in \texttt{best\_first} are \texttt{(priority, counter, state, g)}, and the \texttt{counter} is there for a reason (\figref{fig:tuple}).

\begin{aifig}[How heapq breaks priority ties]{Tuples are compared left to right. When two entries tie on priority, Python compares the next field. The \texttt{counter} guarantees that the next field is a unique integer, so ties resolve by insertion order and the state itself is never compared.}{fig:tuple}

  {Without the counter the heap would compare the states. Strings compare, so airports
   happen to work --- but a tuple state or a mixed type raises \texttt{TypeError}, and even
   when it works the tie is broken by name rather than by the search.};
\end{tikzpicture}
\end{aifig}

\begin{pitfall}
Putting the path list, or any payload, directly after the priority is a correctness smell even when it runs: two equal-priority entries are then ordered by comparing their payloads, so the algorithm's output depends on state names. One unique increasing integer between the priority and the payload makes ties resolve by insertion order and stops the payload from ever being compared.
\end{pitfall}

\section{Testing search code}

A search function can be wrong in ways that a successful run on 6,464 airports never reveals: it may return a path but not the cheapest, count expansions off by one, or loop forever on a cycle. Tests on graphs of four or five states catch these because the correct answer can be worked out by hand. \texttt{utils/test\_search.py} has eight, one per failure mode:

\begin{mltable}
\begin{tabularx}{\linewidth}{@{}>{\bfseries\leavevmode\color{MLNavy}}p{0.34\linewidth}X@{}}
\toprule
\rowcolor{MLPaleBlue!92}
Test & What a failure would mean \\
\midrule
start equals goal & The goal test runs before any expansion; hops and cost are zero. \\
unreachable goal & Failure is reported as \texttt{found=False}, not an exception or a wrong path. \\
cycles terminate & The seen-set stops DFS from looping forever. \\
BFS and UCS optimise different objectives & The two algorithms give different answers on a graph built so that they must. \\
frontier update finds the cheaper path & A state first reached expensively is later replaced by a cheaper route. \\
A$^\star$ matches UCS with an admissible heuristic & The optimality guarantee holds on a hand-checked graph. \\
GBFS is not assumed optimal & The test asserts the \emph{expected} suboptimality rather than pretending it away. \\
negative cost is rejected & The precondition of UCS is enforced with a clear error. \\
\bottomrule
\end{tabularx}
\end{mltable}

One test in full shows the pattern --- a tiny graph, a hand-derived expectation, one assertion:

\begin{lstlisting}[style=aipython]
def test_frontier_update_finds_cheaper_path():
    graph = {"A": [("B", 10.0), ("C", 1.0)], "C": [("B", 1.0)], "B": [("G", 1.0)], "G": []}
    result = ucs(graph, "A", "G")
    assert result.path == ["A", "C", "B", "G"]
    assert result.path_cost_km == pytest.approx(3.0)
\end{lstlisting}

The tests import \texttt{core} only, so they need no dataset, run in well under a second, and can execute on any machine --- including a continuous-integration server that runs them on every commit. That is the practical meaning of ``dataset-free'': a test that needs a 2~MB download is a test that will not be run.

\begin{keyidea}
Test the algorithm on the smallest graph that can expose the bug, and test the dataset loader separately. A test that needs real data to run tests both at once and diagnoses neither.
\end{keyidea}

\section{A command-line interface}

A package that can only be used from a notebook is only half reusable. \texttt{utils/\_\_main\_\_.py} lets Python run the package as a program:

\begin{lstlisting}[style=aiterminal]
cd all_experiments
python -m utils --algorithm astar --start KUL --goal KEF
ASTAR: found=True, hops=4, cost_km=11461.3, expanded=69, runtime_ms=4.20
KUL -> HKT -> LED -> HEL -> KEF
\end{lstlisting}

The module is thirty lines: \texttt{argparse} declares the three options, the loader builds the graph, a dictionary maps the algorithm name to the function, and the result is printed. It contains no search logic and no data cleaning --- it only \emph{calls} them --- which is why the answer it prints is, to the metre, the one Lab~2 found. Lab~3 runs this command as a subprocess from the notebook and asserts that it exits with status~0.

\section{Benchmarking fairly}

Three queries make a demonstration; ten make a benchmark. Lab~3 runs BFS, UCS, GBFS and A$^\star$ on the ten route pairs in \texttt{utils/search\_queries.csv} and summarises them:

\begin{tabularx}{\linewidth}{@{}>{\bfseries\leavevmode\color{MLNavy}}p{0.12\linewidth}>{\centering\arraybackslash}X>{\centering\arraybackslash}X>{\centering\arraybackslash}X>{\centering\arraybackslash}X@{}}

\midrule

\bottomrule

A benchmark is only fair if a few conditions hold, and each one is visible in the notebook.

\begin{itemize}
  \item \textbf{Same graph, same queries, same machine.} Every algorithm sees the identical cleaned graph and the identical ten pairs.
  \item \textbf{Success rate before averages.} A mean cost over the queries an algorithm happened to solve would flatter an algorithm that fails on hard queries. All four succeed on all ten here, which makes the means comparable.
  \item \textbf{Effort in expansions, not milliseconds.} The runtime column is kept but is not the basis for conclusions.
  \item \textbf{Every path validated.} The notebook checks that A$^\star$'s cost equals UCS's on all ten queries and counts the queries on which GBFS is costlier (seven of ten).
\end{itemize}

The result is a recommendation with evidence behind it: for kilometre-based routing, A$^\star$ is the default --- UCS's answer at 2\,\% of UCS's effort. BFS is the right tool only when the objective really is fewest legs; GBFS is an approximation to reach for when effort matters more than the last few percent of cost.
