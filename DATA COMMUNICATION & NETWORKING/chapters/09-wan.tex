\section{HDLC and PPP in the source material}
HDLC and PPP are serial link encapsulations that must match at both ends. PPP also supports network-layer negotiation and authentication through PAP or CHAP.

\begin{tabularx}{\linewidth}{>{\bfseries}p{0.22\linewidth}XX}
\toprule
Feature & HDLC portion & PPP portion\\\midrule
Role in lab & Establish the serial Layer-2 link & Replace HDLC and add authentication capability\\
End agreement & Both ends use HDLC & Both ends use PPP\\
Authentication & Not used in the HDLC section & PAP between R1--R2 and CHAP between R2--R3\\\bottomrule
\end{tabularx}

\section{Step 4: identify the DCE and change the clock rate}
One side of a synchronous serial link provides clocking. Here R1 Serial1/0/0 is the DCE; change its baud rate from 64,000 to 128,000 bit/s.

\begin{vrpbox}{<R1> display interface Serial 1/0/0}
\begin{lstlisting}[style=dcnvrp]
Serial1/0/0 current state : (*\higreen{UP}*)
Line protocol current state : (*\higreen{UP}*)
Description:HUAWEI, AR Series, Serial1/0/0 Interface
Route Port,The Maximum Transmit Unit is 1500, Hold timer is 10(sec)
Internet Address is 10.0.12.1/24
(*\hi{Link layer protocol is nonstandard HDLC}*)
Physical layer is synchronous, (*\hi{Baudrate is 64000 bps}*)
(*\hi{Interface is DCE}*), Cable type is V35, Clock mode is DCECLK
    Last 300 seconds input rate 3 bytes/sec 24 bits/sec 0 packets/sec
    Last 300 seconds output rate 3 bytes/sec 24 bits/sec 0 packets/sec
\end{lstlisting}
\end{vrpbox}
\vrpread{three lines answer three different questions. \cmd{Link layer
protocol} is the encapsulation, and it must match the far end.
\cmd{Interface is DCE} identifies which router owns the clock.
\cmd{Baudrate} is the rate you are about to change --- and it is only
settable on the line that says DCE.}

A synchronous serial link has no separate clock wire, so one end must
generate the timing the other end samples against. That end is the DCE.
The DTE takes whatever rate it is given, which is why \cmd{baudrate} is
rejected or ignored on that side.

[R2] interface Serial 1/0/0

\section{Step 6: configure PAP on R1--R2}
R1 authenticates R2 with PAP.
\begin{lstlisting}[style=dcnterminal]
[R1] interface Serial 1/0/0
[R1-Serial1/0/0] ppp authentication-mode pap
[R1] aaa
[R1-aaa] local-user huawei password cipher huawei123
[R1-aaa] local-user huawei service-type ppp

[R2] interface Serial 1/0/0
[R2-Serial1/0/0] ppp pap local-user huawei password cipher huawei123
\end{lstlisting}
Then retest the R1--R2 link.

\section{Step 7: configure CHAP on R2--R3}
The source text names R1 here, but its topology and commands identify R3 as the authenticator and R2 as the CHAP peer. The sequence below follows the commands.

\begin{lstlisting}[style=dcnterminal]
[R3] interface Serial 2/0/0
[R3-Serial2/0/0] ppp authentication-mode chap
[R3] aaa
[R3-aaa] local-user huawei password cipher huawei123
[R3-aaa] local-user huawei service-type ppp

[R2] interface Serial 2/0/0
[R2-Serial2/0/0] ppp chap user huawei
[R2-Serial2/0/0] ppp chap password cipher huawei123
\end{lstlisting}

\section{Step 8: observe CHAP negotiation with debugging}

The two schemes differ in a way the debug output makes visible. PAP
sends the password across the link; CHAP never does, sending instead a
hash of a challenge the authenticator chose. That is why the CHAP debug
shows a Challenge/Response/Success triple rather than a single request.

\begin{utpfig}[PAP and CHAP]{PAP's two messages against CHAP's three. The password
crosses the link in the left-hand exchange and never crosses it in the
right-hand one.}{fig:pap-chap}
\begin{tikzpicture}
% ---------- PAP ----------
\node[font=\bfseries\small\color{UTPRed}] at (2.1,0.85) {PAP --- 2-way};
\seqactor{p2}{0}{R2 (peer)}{host}
\seqactor{p1}{4.2}{R1 (auth)}{server}
\seqlife{p2}{-2.3}\seqlife{p1}{-2.3}
\seqmsg{p2}{p1}{-0.85}{\tiny username + password}{risk}
\seqmsg{p1}{p2}{-1.65}{\tiny Authenticate-Ack}{arrowb}
\node[font=\tiny\color{UTPRed},align=center,text width=4.4cm] at (2.1,-3.05)
  {Password sent in the clear, once, at the peer's initiative.};

% ---------- CHAP ----------
\begin{scope}[xshift=8.0cm]
\node[font=\bfseries\small\color{UTPGreen}] at (2.1,0.85) {CHAP --- 3-way};
\seqactor{c2}{0}{R2 (peer)}{host}
\seqactor{c3}{4.2}{R3 (auth)}{server}
\seqlife{c2}{-2.3}\seqlife{c3}{-2.3}
\seqmsg{c3}{c2}{-0.7}{\tiny Challenge}{arrowb}
\seqmsg{c2}{c3}{-1.35}{\tiny hash(challenge + password)}{arrow}
\seqmsg{c3}{c2}{-2.0}{\tiny Success}{arrowb}
\node[font=\tiny\color{UTPGreen},align=center,text width=4.6cm] at (2.1,-3.05)
  {Only a hash crosses. The authenticator starts the exchange and can repeat it.};
\end{scope}
\end{tikzpicture}
\end{utpfig}

\begin{keyidea}
The direction of the first message tells you which router is the
authenticator. In PAP the peer speaks first; in CHAP the authenticator
does. Reading that from a debug trace identifies immediately which end
holds the wrong configuration.
\end{keyidea}

Cycle the serial interface and enable PPP CHAP debugging to regenerate negotiation messages and locate authentication failure.

\begin{vrpbox}{<R2> terminal debugging \quad + \quad debugging ppp chap all}
\begin{lstlisting}[style=dcnvrp]
PPP State Change:
  Serial2/0/0 CHAP : ListenChallenge --> (*\hi{SendResponse}*)
PPP Packet:
  Serial2/0/0 Input  CHAP(c223) Pkt, Len 20
  State SendResponse, code (*\hi{Challenge(01)}*), id 1, len 16
  Message: Welcome to ...
PPP Packet:
  Serial2/0/0 Output CHAP(c223) Pkt, Len 33
  State SendResponse, code (*\hi{Response(02)}*), id 1, len 29
PPP Event:
  Serial2/0/0 CHAP Receive Success Event
  State SendResponse --> (*\higreen{ClientOpen}*)
PPP Packet:
  Serial2/0/0 Input  CHAP(c223) Pkt, Len 16
  State ClientOpen, code (*\higreen{Success(03)}*), id 1, len 12
\end{lstlisting}
\end{vrpbox}
\vrpread{the three CHAP codes appear in order --- \cmd{Challenge(01)} inbound,
\cmd{Response(02)} outbound, \cmd{Success(03)} inbound --- which is
\figref{fig:pap-chap} playing out on the wire. A failure stops after the
response, with \cmd{Failure(04)} instead of \cmd{Success(03)}, and that single
code tells you the password is wrong rather than the link.}

\begin{pitfall}
Run \cmd{terminal debugging} first, or the messages are generated and never
displayed. Turn it off with \cmd{undo terminal debugging} when finished ---
debug output on a busy interface makes the console unusable.
\end{pitfall}

\begin{verification}
Verify in order: \textbf{physical state $\rightarrow$ DCE clocking $\rightarrow$ encapsulation $\rightarrow$ IP $\rightarrow$ OSPF $\rightarrow$ authentication $\rightarrow$ ping}.
\end{verification}

\section{Troubleshooting matrix}
\begin{tabularx}{\linewidth}{>{\bfseries}p{0.25\linewidth}X}
\toprule
Symptom & First evidence to inspect\\\midrule
Physical state down & Cabling/serial connection and device/interface state.\\
Physical up, protocol down & HDLC/PPP encapsulation match, DCE clocking, and PPP authentication if enabled.\\
Direct ping works, remote ping fails & OSPF neighbor/routes and the destination routing table.\\
PPP works until authentication is added & PAP/CHAP mode, username, password, AAA local user and service type.\\
CHAP result unclear & Reinitialize the interface as directed and inspect PPP CHAP debug output.\\\bottomrule
\end{tabularx}

\begin{pitfall}
An authentication problem can make the link protocol fail even when the cable and IP address appear correct. Once PAP or CHAP is enabled, the username/password/AAA configuration becomes part of Layer-2 link establishment and must be checked alongside encapsulation.
\end{pitfall}
